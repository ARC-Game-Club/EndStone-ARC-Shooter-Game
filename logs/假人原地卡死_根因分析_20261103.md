# 假人原地卡死 —— 现场日志与根因分析

> 采集时间：2026-11-03 15:44:20（枪战服重启）→ 16:09
> 涉及版本：`arc_shooter_game v0.4.40` + `arc_fake_player v4.2.2` + 行为包 `arc_fake_player_bridge v4.2.2`
> 原始日志：`logs/latest.log`（9657 行，1.6 MB）

---

## 0. 一句话结论

**导航链路本身是通的**（路径请求 → A\* → 路径下发，747 次全部成功），
**卡死发生在"执行"这一步**：行为包 JS 把逐格的路径点当成远距离目标丢给引擎寻路，
而引擎既不会"迈上 1 格"也不会"走下 5 格"——harbor 图里 **9.2% 的边引擎根本做不了**。

另外有 **22 个"站在铁栏顶上"的幽灵节点**（脚高 y=68）在抢假人的吸附点，
把路径起点抬到 4 格高的空中。

## 2. 根因

### 根因 A（Python 端，本次已修，未部署）：路径起点被吸附到 4 格高的铁栏顶

`nav/navmap.py::snap()` 原来用 `(水平距离, 高度差)` 排序：

```python
key = (d, abs(nav.nodes[i][1] - foot))     # ❌ 水平距离优先
```

于是**同一列、高 4 格的节点**会赢过**隔壁列、同高度的节点**：

```
假人在 (-1005.30, 64.00, 979.14)
  → 被吸附到 (-1006, 68, 979)   ← 铁栏顶，y=68，比假人高 4 格
  → 路径第一步就是"向上 4 格" → 引擎走不到 → 每拍重试同一点
```

日志证据 —— 路径「起点 → 终点」的高差分布（64 种配对，共 747 次下发）：

```
dy=-4 : 100 次      ← 起点被抬高了 4 格
dy=+6 : 59 次       ← 终点被抬高了 6 格
dy=+3 : 60 次
dy= 0 : 430 次
```

`(-1006,68,979) → (-1006,64,983)` 这一对单独出现了 **98 次**。

**修法**（本次提交已改）：排序键换成 `(高度差, 水平距离)` ——
物理上假人只能在**当前高度层**活动，高度差必须优先。

### 根因 B（JS 端，**主因，未修**）：把逐格路径点当远距离目标丢给引擎

路径点队列是**逐格相邻**的（相邻格水平距离 1~1.41 格），
但 `behavior_pack/scripts/arena_combat.js` 里的到达阈值是：

```js
const NAV_WP_ARRIVE = 2.2;       // 距路径点这个距离内算到达，切下一个
```

`stepWaypoint()` 每拍会**连续推进多个路径点**：
站在 c0 时，c0(0 格)→c1(1 格)→c2(2 格) 都 ≤2.2 判定为"已到达"，
于是 `idx` 一口气跳到 c3，最终交给 `navigateToLocation` 的是
**3 格开外**的那个点。

这 3 格里只要有一个"上 1 格"或"下坡"，引擎就规划不出完整路径
（`isFullPath=false`）→ 实体一步不动 → `本段已走 0.0 格`。

### 根因 C（JS 端，未修）：引擎寻路做不了"上 1 格 / 下坡"

harbor 烘焙出来的有向边按高差分布（`scripts/nav_graph_stats.py` 实测）：

```
平走 dy=0 : 19362  (90.8%)
上 1 格    :   660  ( 3.1%)   ← 引擎迈不上去（玩家 step height 0.6）
下坡 1-5  :  1313  ( 6.2%)   ← 引擎走不下去
→ 引擎做不了的边 = 9.2%
```

导航网格的规则本身是**对的**（用户 2026-11-03 规格：上 ≤1、下 ≤5），
问题在于**执行侧没有实现这两个动作**。

建议的执行语义（逐格）：

* 平走 → `navigateToLocation(下一格)`，引擎够用；
* 上 1 格 → 引擎规划不出来，需要**先 `sim.jump()` 再走**（`sim.jump()` 在本服可用，
  `main.js` 的 `doJump` 已经在用）；
* 下坡 1~5 格 → 走到边沿自然掉落，或直接给引擎"脚下空气"的目标点。

另外 `NAV_WP_ARRIVE` 在逐格模式下应该降到 **~0.9**（真正走到那一格才算到达），
并加一个**卡住检测**：连续 N tick 位移不足就跳过这个路径点，
连续跳过 M 个就放弃整条路径（退回原来的扇形搜索）。

### 根因 D（词表，已量化，未改）：铁栏/活板门被当实心 → 幽灵节点

`nav/taxonomy.py` 默认从严：**没列进 `PASSABLE_DECOR` 的方块一律当实心**。
实测词表判定：

| 方块 | `is_air_space` | `is_support` | 游戏里实际 | 对不对 |
|---|---|---|---|---|
| `carpet` / `brown_carpet` / `white_carpet` / `moss_carpet` | True | False | 能穿、站不住 | ✅ **对** |
| `snow_layer` | True | False | 同上 | ✅ 对 |
| `wall_banner` / `poppy` | True | False | 能穿 | ✅ 对 |
| `iron_bars` | **False** | **True** | **能穿、站不住** | ❌ 错 |
| `spruce_trapdoor` / `trapdoor` | **False** | **True** | 能穿 | ❌ 错 |
| `arc:sandbag` | False | True | 实心整块 | ✅ 对 |

影响（`scripts/nav_graph_stats.py --thin-as-air` 对比）：

| | 当前词表 | 薄片方块当空气 |
|---|---|---|
| 站立点 | 3774 | **3908**（+134） |
| 有向边 | 21335 | 21933 |
| **「站在铁栏顶上」的幽灵节点** | **22 个（脚高全是 y=68）** | **0 个** |

这 22 个幽灵节点正是根因 A 里"假人被吸到 y=68"的来源。
修法：把 `iron_bars` / `*_trapdoor` 这类**薄片**方块加进 `PASSABLE_DECOR`
（当空气、且不能当地板），然后**重新烘焙**。

### 关于"地毯导致可站立空间不足" —— **已排除，当前就是对的**

用户 2026-11-03 11:12 的怀疑方向：`地毯是没有高度的方块，直接视为空气就好了`。

实测结论：

* `carpet` 本身就在 `PASSABLE_DECOR` 里；
* 而且上游还有 `_PASSABLE_DECOR_SUFFIXES = ("_carpet", "_tulip", "_sapling")`，
  **16 种颜色变体**（`brown_carpet` 等）全都被兜底成空气；
* `is_support()` 对地毯返回 False → 地毯**不能**当地板 ✔

用服务器真实的 `harbor.json` 做对照实验（把地毯强行当实心）：
站立点从 **3774 掉到 3691（少 83 个）**。
也就是说**地毯现在是按空气算的，不用改**。

### 根因 E（次要）：假人身体卡在方块里

1545 条 `arena 卡死` 的「脚/身/头」统计：

```
身=minecraft:iron_bars              ×229   （游戏里能穿）
身=arc:sandbag                      ×151   （实心整块 → 真卡死）
身=minecraft:spruce_trapdoor         ×92   （能穿）
身=minecraft:brown_carpet            ×79   （能穿）
身=minecraft:polished_blackstone_button ×77
```

`arc:sandbag` 那 151 次是**真被埋**（整块方块里），引擎挪不动；
其余是"身体格里有薄片方块"，游戏里能走，但导航词表当成了墙
（→ 真实能走的路在图里不存在 → A\* 绕远或判"不可达"）。

日志里对应的不可达：

```
导航请求无路径 → api_request_path: (-993, 64, 979) → (-1006, 68, 979)
                不可达（分量断开或只有单向跳崖边）
```

> 二轮修复补充（2026-11-03 晚，GLM）：
> - `stepWaypoint` 重写：老实现到达后**递归连推**（根因 B 的确切机制），
>   现在只前进一个点并当拍对新的当前点下发导航；
> - `nav_graph_stats.py` 自带的后缀表副本补上 `_trapdoor`，体检数字与
>   真实烘焙对齐（harbor 词表修复后：站立点 3811 / 有向边 21860 / 幽灵 0；
>   炼狱小镇：48286 / 313629）；
> - 上 1 格判据 `dy∈[0.9,1.6]`：脚部坐标是浮点，站在半砖上时目标格
>   高差可能只有 0.5，用窗口而不是精确 ==1。

> ⚠️ **行为包 JS 改动必须重启服才生效**（BDS 只在开局加载脚本）。
> ⚠️ **JS→Python 的 script event 在 BDS 日志里不打印**
> （只有 Python→JS 会打 `Script event X has been sent`），
> 所以**不能**用"日志里有没有某事件"来判断 JS 有没有发消息——
> 要看 Python 侧的日志。
